- 锁定 Unity `6000.0.76f1`
- 原因是避免升级引起场景和资源批量重新序列化
- 在项目交付前不升级引擎版本

## 2026-09-02：删除奔跑机制

### 原方案
玩家奔跑会加速燃料消耗，Dying 状态下移动会加速熄灭倒计时。

### 实际问题
该机制把移动速度与两套计时器隐式绑定，玩家难以判断火焰究竟为什么快速衰弱，也可能为了节省燃料而被迫缓慢移动。

### 当前决定
删除奔跑动作。玩家采用固定移动速度，移动不影响燃料消耗和 Dying 倒计时。

### 代价
失去“赶路越快、燃烧越快”的风险收益关系。

### 后续验证
如果关卡缺乏时间压力，优先调整火把燃烧时长、关卡距离和氧气分布，不重新加入奔跑。

## 2026-09-02：氧气从连续场改为区域常量

### 原方案
`OxygenField.Sample(pos)` 静态查询，由场景中多个 `OxygenVolume` 叠加插值成连续的氧气场。

### 实际问题
连续插值下，玩家在两个体积交界处火焰缓慢变化，无法反推"我是因为进了哪里才快熄的"。谜题需要的是可判读的因果，不是物理正确的浓度分布。

### 当前决定
改为 `OxygenZone`：一个区域一个常量，trigger 进出即切换，场景外层放默认区域兜底。Flame 每帧读 `currentZone.Oxygen`。

### 代价
失去平滑过渡，跨门口时火焰状态会有一次跳变。

### 后续验证
若跳变太突兀，在 VFX 层做插值缓动，逻辑值仍保持离散。

## 2026-09-02：Flame 保持为逻辑单例，载体保持为接口

### 原方案
一度考虑把 `Flame` 改成 MonoBehaviour 直接挂在场景里，`IFuelCarrier` 改成抽象基类 `FuelCarrier : MonoBehaviour`，理由是方便 Inspector 拖拽装配。

### 实际问题
火在设定上是"唯一且不属于任何物体"的。做成场景对象后，交接时要处理 Transform 归属、跨关卡存活、以及"场景里有两个 Flame"的可能性，反而多出边界。抽象基类还会挡住 `PipeNetwork` 这类已有继承需求的载体。

### 当前决定
`Flame` 维持为不挂物体的逻辑单例，由关卡管理器每帧 `Tick`；载体维持接口 `IFuelSource`，任何 MonoBehaviour 都能实现。

### 代价
载体引用无法直接在 Inspector 里拖（接口不可序列化），需要在代码里通过 trigger / 拾取逻辑赋值。

### 后续验证
若装配确实繁琐，只在编辑器侧加一个 `[SerializeField] MonoBehaviour initialCarrier` 做入口转换，不改动运行时结构。

## 2026-09-02：燃料耗尽即熄灭，不给倒计时

### 原方案
载体 fuel 归 0 时不立即销毁，先让火滑入 Dying 走完 8 秒倒计时，等火转移走或熄灭后载体才 Destroy，以此保证 `_current` 永不为 null。

### 实际问题
这等于给燃料也发了一张 8 秒的免死金牌，Fuel 和 Oxygen 的性质就分不开了。设计文档初稿写的是"载体 fuel 归 0 销毁自己"，且 Fuel 的定位是不可逆资源。

### 当前决定
以初稿为准：fuel 归 0 → 载体销毁 → 火同帧 Extinguished → 关卡失败回检查点。dyingTimer 的 8 秒抢救窗口只对缺氧成因有效。"载体死，火不死"依靠玩家在归 0 前完成 `AttachTo`。

### 代价
`_current` 在火熄灭后为 null，需要在 `Tick` 第一行用 `State == Extinguished` 挡掉。只此一处判空。

### 后续验证
若玩家反馈火把烧尽太突然，靠 Ember 阶段的视觉提示和火把总时长调整，不给燃料加倒计时。

## 2026-09-04：镜头系统执行降级预案

> 开发规划阶段 2 里写着"超两天即执行降级"。这次不是被工期逼的，是**开工前就直接选了降级方案**——
> 下面第 4 条说明为什么早决定比晚决定便宜。

### 原方案
"镜头永远聚焦火种"（简报 3.4）：注视点取玩家与火的**加权中点**，火越远权重越高；同时 FOV 自适应拉远，保证两者始终同框；火脱手超过阈值时镜头明确偏向火，并给方向指示。常态即此。

### 实际问题
1. **注视点会漂，而移动方向是相对镜头算的。** 玩家动一步、火动一步，中点动两步。于是镜头朝向被"火在哪"反向驱动，"向前走"的含义每帧都在变。题目第 3 条硬要求第三人称可操作，这与"镜头由第二个物体驱动"是结构冲突，不是调参能补的。
2. **两条曲线互为补偿。** 加权曲线改了，FOV 曲线要跟着重调；反之亦然。而这类手感参数在阶段 4 有真关卡之前**没有判据**——等于在没有验收标准的情况下同时调两条耦合曲线。
3. **收益几乎全在过场那一刻。** 而过场只要把镜头锚点换成火就能完整拿到，不需要加权。
4. **阶段 2 排在角色控制（阶段 3）之前，场上连一个会动的玩家都没有。** 加权中点的手感要等阶段 3 之后才第一次可判——风险会被推迟到那时才暴露，恰好是规划里"越晚发现越贵"想避免的事。与其花两天做一个当天验不了的东西，不如当天就取降级版并把省下的时间还给关卡。

### 当前决定
`GameCamera.cs` 一个组件、三种模式，差别只有**锚点取谁**：

| 模式 | 锚点 | 用在哪 |
|---|---|---|
| `FollowPlayer` | 玩家（常态） | 标准第三人称：鼠标控 yaw/pitch、球检测防穿墙、固定 FOV |
| `LockOnFlame` | 火本身 | 过场。太空关最后一帧"镜头跟着火离开"就是它 |
| `Hold` | —— | 蒙太奇。实现就是直接 return，一帧都不动 |

- 锚点本来就在做 `SmoothDamp`，所以**切模式的推镜不需要任何过渡代码**，过场只是换一个更长的平滑时间。
- 火跑出画面这条信息交给 `FlameOffscreenIndicator.cs`：屏幕边缘的方向箭头。
- 加权中点 + FOV 自适应的完整模型写进设计文档第 6 章（未实现设计），按"设计描述 / 玩法建模 / 数据结构 / 如何接入 / 未实现原因"格式。

### 代价
1. **常态下火脱手后可能完全不在画面里**——这正是原方案要消灭的问题，现在只靠一个箭头兜底。
2. **引入了全项目唯一一个 HUD 元素**，与"零 HUD"原则（简报 3.5）冲突。缓解手段是把例外压到最小：火在画面内时它**一个像素都不画**；只给方向，不给距离、数字、边框；颜色与闪烁频率全部从 `Flame.State` / `DyingTimer` 派生，不引入任何新状态——"还剩多久"由闪烁频率说，不由数字说。
3. FOV 不再自适应，火离得远时在画面里会很小。
4. "镜头永远聚焦火种"这条独特表现手法被削弱成只在过场成立。它仍然是本作唯一一次镜头脱离玩家，但不再是常态语言。

### 后续验证
- **阶段 4 洞穴段实测**：火放在柴堆前、玩家走开找可燃物时，只有箭头够不够用。不够的话先加最小补丁——"火脱手超过 X 米时锚点朝火偏移一段固定量"，那是**一个参数**，不是整条加权曲线。
- 阶段 4 结束若仍有余量，再考虑把加权中点作为"火脱手时"的局部特例回填，而**不是**恢复成常态。
- 阶段 3 接入真正的角色控制器后复测：转镜头时移动方向是否稳定（这是否决原方案的第 1 条理由，降级版必须在这一条上明显更好，否则降级白降）。

## 2026-09-05：镜头改用 Cinemachine，弃用手写的 GameCamera

> 上一条（2026-09-04）刚定下手写镜头并验收通过，隔天就换掉。**换掉的理由不是它跑得不对，是它交付得不对。**

### 原方案
自己写 `GameCamera.cs`：`SmoothDamp` 锚点 + 单发 `SphereCast` 防穿墙 + 三种模式（锚点取谁）。约 200 行，2026-09-04 十条验收全过。

### 实际问题
1. **作者调不动。** 镜头的全部手感锁在 200 行 C# 里——改一个跟随距离要读代码、改一条阻尼要重新编译、想试试别的构图得先看懂 `Apply()` 在干嘛。作者原话：「我学会用 Cinemachine 比你自己写了一堆摄像头脚本我还看不懂更好」。**交付物不只是"能跑"，还包括"作者能继续改"**——后一项手写版直接不及格，而这一项在笔试里恰恰是重的：镜头参数是要在阶段 4 反复调的。
2. **防穿墙只是单发 `SphereCast`。** 不处理"镜头已经卡在几何体内部"、不管 near clip plane、不沿射线找最近可视点。阶段 4 洞穴段的狭窄空间是已知风险，而这正是 `CinemachineDeoccluder` 的本职。
3. **震屏 / 手持噪声**（阶段 4 野兽突进的反馈）在手写版里要从零做，Cinemachine 的 Impulse + Noise 是现成的。
4. **第一次交付时我根本没把 Cinemachine 列为被否决的方案。** 当时的依据只是"它不在 `manifest.json` 里"——那不是理由，是漏了。CLAUDE.md 4.2 要求写下被否决的方案，我写了"为什么否决加权中点"，却漏掉了评审最可能问的那一个。

### 当前决定
装 `com.unity.cinemachine` **3.1.7**。三台 `CinemachineCamera` + 一个薄切换器 `CameraDirector`（只改 Priority，**类里不出现任何 Vector3 运算**）。

| 手写版里的东西 | 现在归谁 |
|---|---|
| `SmoothDamp` 锚点 | Orbital Follow 的 **Damping** |
| yaw / pitch / 灵敏度 / 上下夹角 | Orbital Follow 的 **Horizontal & Vertical Axis** + **Input Axis Controller** |
| `distance` | Orbital Follow 的 **Radius** |
| `SphereCast` 防穿墙 | **Deoccluder**（Collide Against 用 Layer 排除 Player / Zone） |
| 切模式时的过渡 | Brain 的 **Default Blend / Custom Blends** |
| 三个模式 | 三台 vcam；`CameraDirector` 只负责把选中那台的 Priority 抬起来 |

顺带修掉两个手写版的真实缺陷：

- **`Hold` 的语义原本是错的。** 手写版是"冻结在当前机位"，而简报第 8 章写的是「同一堆篝火、**同一个机位**、同一个焦距」——那是**预先摆好的固定机位**，不是"冻结在玩家碰巧站的地方"。Cinemachine 的固定 vcam 反而更贴设计，换过来顺手改对了。
- **防穿墙的忽略方式从代码挪到了层级。** 原来靠 `QueryTriggerInteraction.Ignore` 一个参数把 `OxygenZone` 挡掉；现在把 zone 放进 `Zone` 层、玩家放进 `Player` 层，Deoccluder 的 Collide Against 不勾这两层。显式、在 Inspector 里看得见，而且**阶段 3 玩家挂上 CharacterController 之后依然成立**——原来那版要求"删掉玩家的 Collider"，那是个撑不到阶段 3 的将就。

### 代价
1. 多一个第三方包依赖。交付时「网络资源备注」要写一条。
2. **Cinemachine 3.x 对 2.x 是破坏性 API 变更**，网上大量教程还是 2.x 的（`CinemachineVirtualCamera`、`Cinemachine` 命名空间），照抄编译不过。已在 `CameraDirector` 注释里写明用的是 3.x（`Unity.Cinemachine` 命名空间、`CinemachineCamera`）。
3. **镜头行为不再能只读代码读出来**，要同时看 Inspector。对交付是净收益（作者调得动），对"一个文件说清全部逻辑"是损失。
4. 扔掉一版已验收通过的代码，约 200 行、一天的量。**这个代价是真金白银，但它买的是"这套镜头在剩下的六个阶段里能被人改"**，比一天贵。

### 后续验证
- 装完包重跑阶段 2 的十条验收。**第 3 条（防穿墙）要重点看**：Deoccluder 的 Strategy 三选一（Pull Camera Forward / Preserve Camera Height / Preserve Camera Distance）得在洞穴里试出哪个最稳。
- 阶段 4 洞穴段实测 Deoccluder——这是换过来的主要技术理由，没验就是没兑现。
- 阶段 7 蒙太奇：确认 Custom Blends 里 `FollowPlayer → Hold` 该用 **Cut**（硬切）还是留一段推镜。简报要的是蒙太奇**期间**不动，切入那一下用哪种没写死，实拍了再定。

## 2026-09-05（同日修正）：删掉 Hold 机位与 CameraDirector 切换器

### 原方案
三种镜头模式 `FollowPlayer / LockOnFlame / Hold`，外加一个 `CameraDirector` 负责在它们之间切。

### 实际问题
1. **`Hold` 是凭空造出来的第三种模式。** 开发规划阶段 2 原文写的是**一个**过场模式——「完全锁定火，用于蒙太奇与太空关最后一帧」，本来就把两个用途归在一起。拆成两个是自作主张。
2. **而且拆错了。** 简报第 8 章：蒙太奇「同一堆篝火、同一个机位、同一个焦距，**变的只有周围的东西**」——**火在蒙太奇里是不动的**。而 `LockOnFlame` 的锚点就是火，目标不动镜头就不动，damping 不产生任何运动。**"镜头绝对不动"是 `LockOnFlame` 的自然结果，不需要另造一个模式去实现它。** 我当时的理由是"固定机位语义更贴"，但那个语义要解决的场景（固定机位而火在动）简报里一个都没有。
3. **`CameraDirector` 的形状也是错的。** 将来真正会加的是**更多台 vcam**（工业关"镜头拉远，第一次让玩家看见这团火在驱动整座工厂"），不是更多种模式。一个三选一的 enum 每加一台机位就要改代码，而 Cinemachine 本来就不需要。
4. 删掉 `Hold` 之后只剩两台，切换器彻底没有存在理由。

### 当前决定
**两台 vcam，零切换器代码。切镜头 = 开关过场那台 vcam 的物体。**

- `CM_FollowPlayer`：Priority `10`、一直开着，永远兜底
- `CM_LockOnFlame`：Priority `20`、**默认关着**；打开就自动接管，关掉就自动退回
- 推镜由 CinemachineBrain 的 Blend 负责
- 阶段 7 的过场触发 = UnityEvent 拖 `GameObject.SetActive`，**一行代码不用写**
- 脚手架的 C 键就是 `cutsceneShot.SetActive(!activeSelf)`，存的是 `GameObject` 而非 `CinemachineCamera`——所以**整个 `Assets/Scripts` 现在没有任何一个文件引用 Cinemachine**

> 顺带否决了 `CinemachineCamera.Prioritize()` 那条路：它只在**多台 priority 相同**时才起作用（把自己推到同级队列顶部）。要靠它切镜头，两台就得同 priority，开场谁 live 就变成了注册顺序说了算，不确定。用 priority 分高低 + 开关物体则完全确定，而且照样能挂 UnityEvent。

### 代价
1. 没有一个集中的"镜头归谁管"的代码入口。查"谁在切镜头"要在场景里翻 UnityEvent 连线，而不是搜一个类名。对这个体量的 demo 可接受，而且这本来就是 Cinemachine 的用法。
2. 少了 `CameraDirector.OnValidate` 那几条防呆（vcam 挂进 Brain 层级会自激）。这条改为写在开发规划 2.5 的装配步骤里——**从编译期检查降级成了文档提醒**，是真实的损失。
3. 又扔掉一版刚写完的代码。这次只有 130 行，但连着上一条一起看，镜头这块两天写了三版。

### 后续验证
- 阶段 7 蒙太奇实拍：确认 `LockOnFlame` 在火静止时**真的一帧不动**（Rotation Composer 的 dead zone 若配得不对可能有微动；真有就换 Hard Look At，那是调参不是加模式）。
- 阶段 6 加"拉远看全厂"机位时验证这个结构：应该只是多一台默认关着的高 priority vcam，**不改任何代码**。改了就说明这个结构还是不对。

### 教训（已写进 CLAUDE.md 6.6）
**不要从枚举的完整性反推需求。** `Hold` 之所以被造出来，是因为"锁定 / 冻结"看起来该配成一对，而不是因为哪个关卡需要它。加一个模式之前先问：**简报里哪一段点名要它？** 答不上来就不要加。
