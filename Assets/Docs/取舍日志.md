## 2026-09-02：删除奔跑机制

### 原方案
玩家奔跑会加速燃料消耗，Dying 状态下移动会加速熄灭倒计时。

### 实际问题
该机制把移动速度与两套计时器隐式绑定，玩家难以判断火焰究竟为什么快速衰弱，也可能为了节省燃料而被迫缓慢移动。

### 当前决定
删除奔跑动作。玩家采用固定移动速度，移动不影响燃料消耗和 Dying 倒计时。

### 代价
失去“赶路越快、燃烧越快”的风险收益关系。

### 后续验证
如果关卡缺乏时间压力，优先调整火把燃烧时长、关卡距离和氧气分布，不重新加入奔跑。

## 2026-09-02：氧气从连续场改为区域常量

### 原方案
`OxygenField.Sample(pos)` 静态查询，由场景中多个 `OxygenVolume` 叠加插值成连续的氧气场。

### 实际问题
连续插值下，玩家在两个体积交界处火焰缓慢变化，无法反推"我是因为进了哪里才快熄的"。谜题需要的是可判读的因果，不是物理正确的浓度分布。

### 当前决定
改为 `OxygenZone`：一个区域一个常量，trigger 进出即切换，场景外层放默认区域兜底。Flame 每帧读 `currentZone.Oxygen`。

### 代价
失去平滑过渡，跨门口时火焰状态会有一次跳变。

### 后续验证
若跳变太突兀，在 VFX 层做插值缓动，逻辑值仍保持离散。

## 2026-09-02：Flame 保持为逻辑单例，载体保持为接口

### 原方案
一度考虑把 `Flame` 改成 MonoBehaviour 直接挂在场景里，`IFuelCarrier` 改成抽象基类 `FuelCarrier : MonoBehaviour`，理由是方便 Inspector 拖拽装配。

### 实际问题
火在设定上是"唯一且不属于任何物体"的。做成场景对象后，交接时要处理 Transform 归属、跨关卡存活、以及"场景里有两个 Flame"的可能性，反而多出边界。抽象基类还会挡住 `PipeNetwork` 这类已有继承需求的载体。

### 当前决定
`Flame` 维持为不挂物体的逻辑单例，由关卡管理器每帧 `Tick`；载体维持接口 `IFuelSource`，任何 MonoBehaviour 都能实现。

### 代价
载体引用无法直接在 Inspector 里拖（接口不可序列化），需要在代码里通过 trigger / 拾取逻辑赋值。

### 后续验证
若装配确实繁琐，只在编辑器侧加一个 `[SerializeField] MonoBehaviour initialCarrier` 做入口转换，不改动运行时结构。

## 2026-09-02：燃料耗尽即熄灭，不给倒计时

### 原方案
载体 fuel 归 0 时不立即销毁，先让火滑入 Dying 走完 8 秒倒计时，等火转移走或熄灭后载体才 Destroy，以此保证 `_current` 永不为 null。

### 实际问题
这等于给燃料也发了一张 8 秒的免死金牌，Fuel 和 Oxygen 的性质就分不开了。设计文档初稿写的是"载体 fuel 归 0 销毁自己"，且 Fuel 的定位是不可逆资源。

### 当前决定
以初稿为准：fuel 归 0 → 载体销毁 → 火同帧 Extinguished → 关卡失败回检查点。dyingTimer 的 8 秒抢救窗口只对缺氧成因有效。"载体死，火不死"依靠玩家在归 0 前完成 `AttachTo`。

### 代价
`_current` 在火熄灭后为 null，需要在 `Tick` 第一行用 `State == Extinguished` 挡掉。只此一处判空。

### 后续验证
若玩家反馈火把烧尽太突然，靠 Ember 阶段的视觉提示和火把总时长调整，不给燃料加倒计时。
